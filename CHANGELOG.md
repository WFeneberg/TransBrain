# Changelog

All notable changes to this project are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- Choice between self-hosted and public map services: tour route planning (`GET /api/tours/{id}/route`) can use either the self-hosted OpenRouteService container (default, unchanged) or the public `api.openrouteservice.org` with a personal API key, and geocoding can likewise use the public `nominatim.openstreetmap.org` instead of the self-hosted Nominatim container — no key, but a strict fair-use policy, whose required identifying `User-Agent` is sent automatically (configurable as `Nominatim:UserAgent`, replace it with your own contact for serious use). Switch per machine with `OpenRouteService:Mode` and `Nominatim:Mode` (`SelfHosted`/`Online`): in the AppHost via user secrets (plus `Parameters:ors-api-key`; geocoding follows the routing choice unless `Nominatim:Mode` pins it, an online service's container and import are skipped entirely, and with both online no OSM extract is needed at all) or directly on the Api (`OpenRouteService__Mode`, `OpenRouteService__ApiKey`, `Nominatim__Mode`), which also gives the Docker Compose and Azure setups, which ship no map containers, a maps option for the first time. The map-status endpoint probes the public routing service with a quota-free empty directions request (its `/v2/health` exists only self-hosted): available means reachable with an accepted key, and no OSM data date is reported because the public service keeps its own data current; the public Nominatim answers the same status probe as the container. A German setup guide (`docs/ONLINE_KARTENDIENSTE.md`) walks through the registration at the public services, both configuration variants and troubleshooting
- Invoice printing and e-invoicing: issued and paid invoices can be downloaded as a print-ready PDF (`GET /api/invoices/{id}/pdf`, German layout with letterhead, line table, totals and a payment note with IBAN — or a payment-received note once paid) and as an electronic invoice in UBL 2.1 XML following XRechnung 3.0 (`GET /api/invoices/{id}/xrechnung`), the format German authorities and business customers require. Both are reads open to every role, but only for documents: a draft or cancelled invoice answers `409 Invoice.NotADocument`. Seller identity (name, address, VAT id, IBAN, contact) comes from the new `InvoiceSeller` configuration section, shipped with sample data to replace before production. Both frontends show "PDF herunterladen"/"XRechnung herunterladen" buttons on the invoice detail for issued and paid invoices; dispatch (e-mail) remains manual — the files are downloaded, not sent. PDF rendering uses PDFsharp/MigraDoc 6.2.4 (the last MIT release; 6.5.0 moved to AGPL/commercial licensing) with embedded DejaVu fonts so rendering works without installed system fonts, e.g. in Linux containers
- Freight billing ("Frachtabrechnung"): invoices for delivered orders. New `Invoice` aggregate with lifecycle `Draft` → `Issued` → `Paid` (cancel allowed from `Draft`/`Issued`); invoice numbers in the form `RE-2027-00042` from an atomic per-year database counter, assigned at creation. An invoice belongs to one customer and carries one line per order (order number, cargo description, net amount), a VAT rate (0–100 %, default 19 %), and computed net/VAT/gross totals (rounded half away from zero). Customer name, billing address, `VatId` and payment term are snapshotted onto the invoice at creation, so later customer edits do not change existing invoices; issuing stamps the issue date and computes the due date from the snapshotted payment term. Only `Delivered` orders can be billed, each order at most once (concurrently creating two invoices over the same order answers `409`); cancelling an invoice frees its orders for re-billing. Endpoints under `/api/invoices`: `POST /` (create draft from customer + orders with per-order net amounts), `GET /` (paged list, `status`/`customerId` filters), `GET /billable-orders` (delivered orders not yet billed), `GET /{id}`, `POST /{id}/issue`, `POST /{id}/pay`, `POST /{id}/cancel`; writes require dispatch rights (`admin`/`disponent`), reads include `viewer`. Both frontends get an invoice list with status filter, a creation form (customer select, billable-order picking with per-order amounts, VAT rate, live totals preview), and a detail view with issue/mark-paid/cancel actions and a "Rechnungen"/"Invoices" navigation entry; operator guides updated (migration `AddInvoices`)
- Map material status on the geodata page: `GET /api/geodata/map-status` (`Read`) probes both self-hosted map services — Nominatim via `/status`, OpenRouteService via `/v2/health` — and reports per service whether it is available and the OSM data date it serves (`null` when a service does not report one); an unreachable service is a regular answer, never an error. The response also describes the installed OSM extract by parsing the PBF file header (no import, dependency-free): Geofabrik region path such as `europe/germany/bayern/oberbayern`, file data timestamp, size and bounding box. Both frontends show the result as a status card above the geodata list (Ready/Unavailable per service plus "OSM data from …", and a "Map extract" line with region, size and file date), hidden when the status call itself fails. Updating the map material stays a server-side task by design (the import runs minutes to hours inside the containers): the new `scripts/update-osm-extract.py` downloads a Geofabrik extract to `data/osm/region.osm.pbf` and removes the `transbrain-ors`/`transbrain-nominatim` volumes so the next AppHost start re-imports; operator and developer guides explain the procedure
- Geodata maintenance ("Geodaten-Wartung"): manual coordinate overrides for addresses the geocoder does not know (its Nominatim instance only covers the imported map extract). New `GeoOverride` aggregate keyed by the normalised address; `LocationResolver` now resolves override → Redis cache → geocoder, so manual coordinates take precedence everywhere (customer location position, order locations, tour routes). Endpoints under `/api/geodata`: `GET /api/geodata` lists every address used by orders and customer locations with its status (`Manual`/`Geocoded`/`Unresolved`) and usage counts, plus orphaned overrides marked "not in use"; `PUT /api/geodata/overrides` upserts an override (`admin` only), `DELETE /api/geodata/overrides/{id}` removes it (the address falls back to the geocoder), `POST /api/geodata/resolve` probes a single address (`503` when the geocoder is unavailable). Both frontends get a "Geodata" page `/geodata` (menu entry for `admin`) with filter, status toggles, per-row try-geocoding/set-coordinates/remove actions and a coordinates dialog; operator guides and e2e specs updated (migration `AddGeoOverrides`)
- `scripts/seed-testdata.py`: seeds a running dev stack through the API with 5 drivers, vehicles, customers, orders and tours (dates relative to today, covering expired/expiring licences and documents and every tour status); refuses to run on a non-empty database. See the developer guide, section 4
- Customer additional data ("Zusatz"), modelled on the legacy customer screen: a secondary address (name, street, postal code, city, ISO country), founding date (not before 1800), number of workers and salaried employees (0–1,000,000), the flags pallet check, toll not on invoice (customer) and reimburse toll (subcontractor), a customer class and a comment (up to 2,000 characters). Customer requests and `CustomerResponse` carry it as a nested `additional` object (omitted means "none", `PUT` replaces it as a whole); invalid values answer `400` keyed by the dotted path, e.g. `Additional.WorkerCount`. Customer classes are a new catalog kind `CustomerClass` under `/api/vehicle-catalog/{kind}` with the legacy class "Huter Vils alle Gattungen" (`HuterVilsAll`) seeded; unknown or newly chosen inactive codes answer `400` keyed `Additional.CustomerClass`, and classes still used by customers cannot be deleted (`409`). Both frontends show a new "Additional data" card in the customer form and a "Customer master data" page `/customer-catalog`, reachable from the customer list (migration `AddCustomerAdditionalData`)
- Vehicle commercial data, insurance, special documents and data sheet, modelled on the remaining pages of the legacy vehicle screen (Seite3, Sonderpapiere, Bemerkungen, Datenblatt). Vehicle requests and `VehicleResponse` carry a nested `commercial` object (purchase price in EUR, purchase date, odometer at purchase, first registration, planned useful life in years/km, cost centre, vehicle and transport insurer with their policy numbers; `PUT` replaces it as a whole, errors keyed e.g. `Commercial.PurchasePrice`) and a free-text `dataSheet` (up to 10,000 characters, kept verbatim). Insurers and document types are two new maintainable catalogs (`InsuranceCompany`, `DocumentType`; common German document types such as ADR, ATP, CEMT, tachograph and UVV are seeded). Special documents are maintained per vehicle under `/api/vehicles/{id}/documents` (type, last check, valid until, remark, last change; one document per type and vehicle, `409` otherwise; removed with the vehicle). Both frontends show new "Commercial", "Insurance", "Special documents" (with expiry status) and "Data sheet" cards in the vehicle form; "Notes" stays the existing notes field (migration `AddVehicleCommercialDataAndDocuments`)
- Vehicle equipment ("Ausstattung"), modelled on page 2 of the legacy vehicle screen: partition wall, pallet basket, dangerous-goods equipment, dangerous-goods approval (ADR), lift axle, double deck, double-deck beams, small/large ladder, tank volume (l), interior length/width/height (mm), and the number of support poles, load bars, lashing straps, pallets, chain tensioners and marble racks plus the marble-rack material (`Steel`/`Aluminium`). Vehicle requests and `VehicleResponse` carry it as a nested `equipment` object (omitted means "none", `PUT` replaces it as a whole); out-of-range values answer `400` keyed by the dotted path, e.g. `Equipment.TankVolumeLiters`. Both frontends show it as a new "Equipment" card in the vehicle form (migration `AddVehicleEquipment`)
- Maintainable vehicle master-data lists ("Fahrzeug-Stammdaten"): vehicle classes and carrier groups are now catalogs with code, name and active flag, maintained under `/api/vehicle-catalog/{kind}` (`VehicleClass`, `CarrierGroup`; writes `admin` only) and on the new page `/vehicle-catalog` in both frontends (reachable from the vehicle list). Vehicles store the entry's code; unknown or newly chosen inactive codes answer `400` keyed `VehicleClass`/`CarrierGroup`, an inactive code a vehicle already has may be kept. Codes are fixed once created, entries still used by vehicles cannot be deleted (`409`) — deactivate them instead. The former fixed vehicle classes are seeded with German names (migration `AddVehicleCatalog`); the vehicle form offers both lists as selections and the vehicle list shows the catalog names
- Extended vehicle master data, modelled on the legacy vehicle screen: confidential-plate flag, make, model, first registration (month/year), power (kW), vehicle class (body type, e.g. tarpaulin, refrigerated, tank), carrier group, default driver, chassis (VIN) and engine number, outer dimensions L/W/H in mm, curb weight, gross weight and max. fifth-wheel load (kg) and free-text notes. `CreateVehicle`/`UpdateVehicle` accept the new fields as optional (`404` for an unknown default driver, `400` keyed by field for out-of-range values); `VehicleResponse` carries them plus `modifiedAt`/`modifiedBy`, stamped on every write. Deleting a driver clears them as default driver on their vehicles (migration `AddVehicleMasterData`)
- `POST /api/vehicles/{id}/status` (`admin`) sets a vehicle to `Available`, `InWorkshop` or `Decommissioned`; reviving a decommissioned vehicle answers `409`
- Redesigned vehicle screens in both frontends: searchable, filterable and sortable list with status chips, delete confirmation and status actions; the vehicle form is grouped into sections (general, technical data, dimensions & weights, notes) and shows who last changed the vehicle

- `Customer` aggregate with `Create`/`Update`/`Delete`/`GetById`/`List` use cases and endpoints under `/api/customers`: company name, registered address (the shared `Address` value object), contact person, e-mail, phone, UID (`VatId`) and payment term in days (0–365); writes require the `admin` role, reads the same roles as the other master data; list responses are cached and invalidated on every write, like drivers and vehicles
- Map for delivery locations: `GET /api/customers/{id}/locations/{locationId}/position` resolves the location address and both frontends show it on the location form. Geocoding now uses Nominatim (OpenStreetMap), which is free and needs no API key; it answers `503` when Nominatim is unreachable and `404` when the address is unknown
- Geocoding for order addresses also moved from OpenRouteService to Nominatim, so the order map no longer needs an OpenRouteService key. Routing (route planning for tours) still uses OpenRouteService and needs its key
- Orders can take their consignee from a customer delivery location: `CreateOrder`/`UpdateOrder` accept an optional `consigneeLocationId` (checked, `404` if unknown; the consignee address is still stored on the order as a copy), the order response carries it, and the order form in both frontends pre-fills the consignee from a chosen location. Deleting a location clears the reference on existing orders. New endpoint `GET /api/customer-locations` lists every location with its customer name
- Delivery locations (`Anlieferorte`) per customer: each has its own name, address and contact person, independent of the customer's registered address. Endpoints under `/api/customers/{id}/locations`, editable from the customer form in both frontends; deleting a customer removes its locations
- Customer list and form in both frontends (`/customers`, `/customers/new`, `/customers/{id}`) and a „Kunden“/„Customers“ navigation entry for `admin`, `disponent` and `viewer`; `docs/BEDIENUNG_TRANSBRAIN_WEB.md` and `_VUEWEB.md` describe the new screens and the roles
- Route planning for tours: `GET /api/tours/{id}/route` returns the truck route through the stops in sequence (OpenRouteService, `driving-hgv` profile), with distance, driving time and a timeline of driving, breaks and stop services
- Driving-time planning under Regulation (EC) No 561/2006: 45-minute break after 4 h 30 min of continuous driving, 9 h daily driving with a 10 h extension warning, 11 h daily rest, and the Sunday truck driving bans in Germany and Austria; countries outside the EU/EEA/CH/GB regime are reported as not modelled
- Customer map: `GET /api/orders/{id}/locations` geocodes the consignor and consignee; both frontends show them on the order form, and the tour detail shows the route, the timeline and the rule violations
- `ErrorType.Unavailable` mapped to HTTP `503`, for an external service that is unconfigured or unreachable
- Both frontends are multilingual: German (default) and English, switchable from the toolbar/app bar and remembered per browser; `docs/BEDIENUNG_TRANSBRAIN_WEB.md` and `docs/BEDIENUNG_TRANSBRAIN_VUEWEB.md` describe the switch
- Developer guide (`docs/DEVELOPER_GUIDE.md`) and installation guide (`docs/INSTALLATION.md`) covering local Aspire, Docker Compose and Azure Container Apps
- Dockerfiles for the API and both frontends, `docker-compose.yml`, a Keycloak production image with its own realm template (`deploy/keycloak`) and `infra/main.bicep` for Azure
- `Database:MigrateOnStartup` setting that applies EF migrations at start outside Development
- Runtime `config.js` in both frontends so the OIDC authority is configured per container instead of being compiled in
- Clean Architecture solution layout with Domain, Application, Infrastructure and Api layers
- Hand-rolled CQRS mediator with validation and logging pipeline behaviors
- Result pattern with `Validation`, `NotFound`, `Conflict` and `Forbidden` error types
- Vehicle aggregate with `Create` and `List` use cases
- PostgreSQL persistence via EF Core 10 with an initial migration
- .NET Aspire orchestration for PostgreSQL, Redis and Keycloak with realm import
- Keycloak authentication with the realm roles `admin`, `disponent`, `fahrer` and `viewer`
- Angular 22 frontend with Material, OIDC login and vehicle list
- Vue 3 frontend with Vuetify, OIDC login and vehicle list
- Integration tests using Testcontainers and a test authentication scheme, using AwesomeAssertions rather than FluentAssertions (FluentAssertions became proprietary from version 8)
- CI workflow building the solution, running .NET tests and building both frontends
- `Driver` aggregate end to end (domain, `Create`/`Update`/`Delete`/`GetById`/`List` use cases, API endpoints, and both frontends' driver list and form)
- `Vehicle` CRUD completed with `Update`, `Delete` and `GetById`, alongside the existing `Create`/`List`
- List filters on both aggregates: `status` and `type` for vehicles, `status` for drivers, in addition to `page`/`pageSize`
- Redis caching for list and get-by-id reads on both aggregates, invalidated by key prefix on every write; caching is disabled entirely (writes are skipped, not merely a slower path) when no Redis connection string is configured, because caching without the ability to invalidate is a correctness hazard, not a performance win
- Per-field validation errors: FluentValidation failures are now grouped under their real field name in the API's `ValidationProblem` response, letting both frontends' forms bind a server-side error onto the matching field instead of only showing a form-level message
- A fallback authorization policy requiring an authenticated user on every endpoint, so an endpoint that forgets `RequireAuthorization` fails closed instead of silently being public; the trade-off, recorded in the spec (§9), is that an unmatched route now answers `401` rather than `404` for an unauthenticated caller
- Application-layer line-coverage gate in CI, failing the backend job when the `TransBrain.Application.Tests` suite's line coverage drops below the spec's 80% floor (measured at 86.9% line / 84.7% branch when the gate was added)
- German-language operator guides for both frontends (`docs/BEDIENUNG_TRANSBRAIN_WEB.md`, `docs/BEDIENUNG_TRANSBRAIN_VUEWEB.md`)
- `Address`, `Cargo` and `TimeWindow` value objects in `TransBrain.Domain/Common`, shared by the order aggregate and reusable by later ones
- `TransportOrder` aggregate end to end (domain, `Create`/`Update`/`Cancel`/`GetById`/`List` use cases, API endpoints, and both frontends' order list and form)
- Collision-free order numbers in the form `TB-2027-00042`, handed out by an atomic per-year database counter (`INSERT ... ON CONFLICT DO UPDATE ... RETURNING`) rather than a `SELECT MAX(...) + 1`, so two concurrent creates cannot receive the same number; a unique index on the column stays as a second line of defence
- Order status machine (`Draft` -> `Planned` -> `InTransit` -> `Delivered`, with `Cancel` allowed only from `Draft` or `Planned`), owned entirely by the entity and returning a `Conflict` for a refused transition rather than silently declining. Only `Cancel` has an endpoint in this phase; the other transitions are driven by tour operations in a later one
- Order list filters: `status`, `pickupFrom` and `pickupTo`, in addition to `page`/`pageSize`
- `Tour` aggregate end to end (domain, `Create`/`AssignOrder`/`RemoveOrder`/`Start`/`Complete`/`GetById`/`List` use cases, API endpoints, and both frontends' tour list, form and detail screens)
- Tour capacity invariants: the sum of the assigned orders' weight and load meters must fit the vehicle, checked against the whole tour rather than the incoming order alone
- Tour assignment invariants: the vehicle must be `Available`, the driver `Available`, and the driver's licence valid on the tour date (a licence expiring exactly on that date still counts)
- Double-booking protection: unique indexes on `(tour_date, vehicle_id)` and `(tour_date, driver_id)` make a second tour for the same vehicle or driver on the same day impossible, including under concurrent requests — a pre-flight query could not
- Stops are derived, not entered: assigning an order creates exactly one `Pickup` and one `Delivery` stop, the pickup always first; removing it drops both and renumbers the rest contiguously
- The order status machine is now driven end to end by tour operations, as spec §5.4 draws it: assigning plans an order, starting a tour puts every assigned order `InTransit`, completing it marks them `Delivered`
- `TransportOrder.ReturnToDraft`, so an order removed from a tour becomes assignable again instead of being stranded in `Planned` — a transition the spec's diagram omits but its `RemoveOrder` use case requires
- `ICurrentUser` abstraction and driver-scoped authorization: a `fahrer` sees only their own tours and may start and complete only those, enforced in the handlers because a policy cannot see which tour a request addresses

- Role-based home page in both frontends at `/`, replacing the vehicle list as the landing screen: per-role counts, work lists and area tiles, driven by a capability table derived from the `realm_access.roles` claim. A dispatcher gets the draft orders awaiting a tour; a driver gets their own tours for today with `Start tour` / `Complete tour` inline, on a layout narrow enough for a phone in the cab
- Navigation shell in both frontends (toolbar with role-filtered links, signed-in user and a **Sign out** button), and route guards that redirect a user without the required capability back to the home page. The list routes are deliberately left unguarded beyond authentication, because `Policies.Read` admits every role
- Sign-out in both frontends, which neither had before
- A `realm-roles-in-id-token` protocol mapper on the `transbrain-spa` client, so `realm_access.roles` reaches the id token and userinfo in the same shape the API already reads from the access token; without it a client cannot see its own roles without parsing an access token that is not addressed to it
- Playwright `home.spec.ts` in both frontends: all four realm roles, sign-out, and the route guards — 30 tests per frontend in total

### Fixed
- Unticking "License plate confidential" on an existing vehicle now persists. EF Core treated `false` as "not set" on the model-level column default and left the old `true` in the database; the default is now only applied by the migration

### Changed
- Tour page in both frontends: when a stop address cannot be placed on the map (unknown, or outside the loaded map extract), the route section now shows a translated message naming that address instead of the raw server text with "HTTP 404"
- Route planning and geocoding are now self-hosted: the Aspire AppHost starts an OpenRouteService container (`driving-hgv`) and a Nominatim container that both read `data/osm/region.osm.pbf`, downloaded once by hand. No external service and no API key any more; `OpenRouteService:ApiKey` and the error `Routing.NotConfigured` are gone, `Nominatim:BaseUrl` is new. Coverage is the loaded map extract (developer guide, section 4.1). Map background tiles still come from `tile.openstreetmap.org`
- Aspire AppHost: Postgres now uses a persistent data volume, so data survives an AppHost restart (Keycloak still re-imports its realm on every start)
- All screens in both frontends now use the vehicle screen design: page header with a count line, a filter bar with search (drivers and tours also by status), sortable tables with status chips, icon actions and an empty state; forms are grouped into cards with a sticky Cancel/Save bar; the home page shows KPI cards and work lists. Deleting a driver, customer or delivery location now asks for confirmation (in TransBrain.Web, cancelling an order does so in a dialog). The driver list also shows "License valid until" (TransBrain.Web marks expired and soon-expiring licences), and the tour detail moves Start/Complete into the page header. The operator guides and their screenshots, including new customer list and form screenshots, are updated
- The carrier groups of the legacy vehicle screen are seeded: Sonstige (`Other`), Huter Vils (`HuterVils`), Huter Füssen (`HuterFuessen`), Fixe Frächter (`Fixed`), Regelmäßig beschäftigte Frächter (`Regular`) and Leihfahrzeuge (`Rental`). Migration `SeedLegacyCarrierGroups` skips any group whose code already exists in any letter case
- The seeded vehicle classes now match the legacy list: Sonstige (`Other`), Tank, Kühler (`Refrigerated`, formerly "Kühlkoffer"), Plane (`Tarpaulin`), Kipper (`Tipper`) and the new Leihfahrzeug (`Rental`). Migration `AlignVehicleClassesWithLegacy` deletes the retired classes Koffer, Silo, Pritsche, Container, Autotransporter and Tieflader, or only deactivates them while a vehicle still uses them; a renamed "Kühlkoffer" keeps its custom name
- Vehicle types now match the legacy vehicle screen: `Tractor` ("Zugmaschine") and `SemiTrailer` ("Hänger (Sattel)"). `RigidTruck` and `Van` are retired and answer `400` (`Vehicle.UnknownType`); existing vehicles of those types become `Tractor` (migration `RestrictVehicleTypes`, not reversible). A semi-trailer cannot drive a tour on its own: creating a tour with one answers `409` (`Tour.VehicleNotMotorized`), and both tour forms offer tractors only. The Sunday truck driving ban now applies to every tour, since the van exemption has no vehicle type left
- `ICurrentUser` exposes `UserName` (Keycloak `preferred_username`, falling back to the subject) for audit stamps
- Write actions are now hidden from roles that may not perform them, in every screen of both frontends, instead of being offered to everyone and refused by the API with a `403`. The operator guides' "Rollen und Rechte" chapters said the opposite and have been rewritten
- Both frontends run their OIDC `checkAuth()` / `auth.load()` exactly once, in the app shell, instead of once per screen — nine components in the Angular app, five views in the Vue app
- The tour list now asks for the API's maximum page size too. The earlier change below covered the vehicle, driver and order lists but missed this one, which asked for no page size at all and so inherited the default of 20; with lists sorted ascending, that hid every tour planned after the twentieth
- The initial-bundle warning budget for the Angular app rises from 500kB to 600kB: the navigation shell belongs in the root bundle permanently and pushed it 3kB over
- Both Playwright suites warm the dev server and Keycloak up once before the first test, so the cold-start cost stops landing on whichever test authenticates first
- Both frontends' list screens and pickers now request the API's maximum page size instead of the default 20. Lists come back sorted ascending, so one default page showed the twenty *oldest* records and hid everything added since — with no pagination controls to reach the rest. This is a stopgap; real paging is still needed above 100 rows
- Vuetify data tables in the Vue frontend no longer paginate a second time on top of the server's page, which could hide a record the server had returned
- The vehicle and driver forms now hydrate the OIDC session before their first request, so a form opened by direct navigation (a bookmark, a page reload) no longer answers `401` to a signed-in user — the same fix the order form received earlier
- The API's response language (FluentValidation's validation messages) is now pinned to English (invariant culture) at startup, rather than following the host machine's ambient culture; see README.md's "API response language" section for the two lines to change together to switch to German instead
